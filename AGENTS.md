# finlite Agent Rules

## Project

finlite is a desktop-first, single-ledger financial assistant for a health-management company.

**Target Users:**

- Accountants / cashiers doing daily bookkeeping
- Reviewers confirming balances and vouchers
- Admins maintaining subjects, fee rates, backups

**Technology Stack:**

- Go 1.25+
- Wails3 `v3.0.0-beta` (Go backend + WebView)
- Frontend: Svelte 5 + TypeScript + Vite (`frontend/`)
- Database: SQLite, single file `finlite.db` (pure-Go driver, e.g. `modernc.org/sqlite`)
- Money: `shopspring/decimal` (never `float64` for amounts)

**It is NOT:**

- a marketing website / landing page / portfolio
- a multi-company SaaS (single ledger for MVP)
- a generic accounting platform (health-management flow only for MVP)

**Business Source of Truth:**

- `docs/business/00-overview-health-finance-flow.md` is normative.
- If code conflicts with the business doc, the business doc wins. Update the doc first, then code.

**MVP Flow (must keep working):**

```
Import (bank/order TSV) -> Bank/Order lists -> Reconcile by settle_date
  -> Data summaries (draft->reviewed->vouchered) -> Vouchers (draft->audited) -> Balance report
```

## Directory Rules

Backend MUST follow:

```
main.go                      # thin entry, embed frontend/dist only
internal/app/app.go          # Wails app + window + service registration
internal/services/*.go       # one Service per domain, exposed to frontend
internal/store/*.go          # SQLite open/migrate/query helpers only
internal/decimal/*.go        # money parsing/formatting wrappers
``` 

Frontend MUST follow:

```
frontend/src/routes/        # pages: import, bank-flow, order-flow, recon, summary, voucher, balance, settings
frontend/src/lib/           # reusable components, format helpers, api wrappers
frontend/bindings/          # GENERATED by Wails, never hand-edit
```

- Pages in `routes/`, reusable UI in `lib/`. Do not put reusable components inside route files.
- Frontend NEVER touches SQLite directly. All data goes through Wails Service bindings.

## Document Creation Rules

Applies to every new document under `docs/` — enough on their own for a plain "create a feature doc" task:

- Filename: `NN-type-topic.md`
  - `NN` — two-digit sequence, use the next after the highest existing (`00`, `01`, ...)
  - `type` — short English category (`overview`, `design`, `message`, `storage`, ...)
  - `topic` — lowercase English words separated by `-`
  - Example: `01-design-message-routing.md`
- Frontmatter: must contain `title` and `description`
- Changelog (if any): `docs/changelogs/YYYYMMDD_feature_name.md`
- Renaming a document: update all in-repo references

---

## Git Commit Rules

- Every `git commit` MUST first generate the summary log file, then commit. Order is mandatory: log first, commit second. A commit without its log file is a failure.
- Log path: `docs/changelogs/YYYYMMDD_feature_name.md` (`YYYYMMDD` = commit date, `feature_name` = lowercase English with underscores, matching the commit scope).
- Naming is exempt from the `NN-type-topic.md` rule; frontmatter (`title`, `description`) is still required.
- Log content: what changed (`Added`/`Fixed`/`Changed`/`Docs` sections), scope/impact, verification results (`gofmt`, `go vet`, `go build`, `npm run check` where applicable). Anonymization rules apply to log content.
- The log file MUST be staged and committed together with the code change in the same commit.

---

## Anonymization Rules

- Applies to all files except `docs/raw/anonymization_mapping.tsv`.
- Never use real company or personal names. Use names from the mapping table only.
- Mask account, merchant, and phone numbers (e.g. `1001****7575`).
- Apply the mapping table first (longest exact match), then mask numbers.
- `docs/raw/anonymization_mapping.tsv` is the only file allowed to contain original values.
- Raw fixtures and demo data must already be anonymized.
- Before finishing, grep for known original values. Any match outside the mapping table is a failure.
- Never commit, push, or force-add files containing original values.

## Financial Rules

- Money: `shopspring/decimal` end-to-end. Store as `TEXT` in SQLite, 2 decimals for display. Never `float64` arithmetic.
- Dates: `YYYY-MM-DD` for business dates, `RFC3339` for timestamps. Income attribution uses order `settle_date` (T+1), not `txn_time`.
- Fee rates: debit `0.5%`, credit `0.6%`, WeChat/Alipay `0.25%`. Auto-compute is a prefill; manual edit sets `fee_manual_adjusted=1`.
- Bank balance check is strict exact equality, NO tolerance:
  `balance == prev_balance + in - out`, and `last - first == sum(in) - sum(out)`.
  Mismatches still import, flagged `mismatch`, cleared only by per-batch manual confirm (`balance_confirmed_at`). Revocable.
- Triple-match (per settle date): `sum(order.net) == bank POS inflow == sum(summary.actual_income)`. Diffs go to a pending queue, never block other rows.
- Vouchers must balance (`sum(debit) == sum(credit)`). Only `reviewed` summaries can generate vouchers. One summary -> one voucher.
- Raw tables (`bank_flows`, `order_flows`) are read-only. No UPDATE API. Fix by void-and-reimport or adjustment rows.
- Every summary edit / audit / voucher action writes `audit_logs` with old/new JSON.
- User-facing errors in Simplified Chinese, actionable (e.g. `借贷不平：借 12000.00 ≠ 贷 11970.00`).
- Amounts, currencies, percents formatted consistently in UI.
- Anonymization (mandatory for all business docs in `docs/`): see `Anonymization Rules` above. Samples and error messages must use anonymized values.

## Coding Rules

**Prefer:**

- Small focused Services and pure helpers
- Explicit `database/sql` + raw SQL, single-writer mutex, WAL mode
- `context.Context` as first Service param where blocking/DB work happens
- Return `(T, error)` from Services; Wails generates TS bindings
- Svelte 5 runes (`$state`, `$props`, `$derived`), TypeScript strict, small components

**Go example:**

```go
func (s *VoucherService) CreateVoucher(ctx context.Context, req CreateVoucherReq) (Voucher, error)
```

**Avoid:**

- ORMs (GORM, sqlc codegen, etc.) unless explicitly requested
- CGO drivers (`mattn/go-sqlite3`) — prefer pure-Go for Wails cross-builds
- `float64` for money, `panic` in Services, `log.Fatal` outside `main.go`
- Business logic in Svelte components (formatting only)
- Hand-editing `frontend/bindings/`
- New dependencies without justification
- Large refactors or touching unrelated files

---

## UI Rules

- Dense, desktop-first tables: sticky header, right-aligned money with tabular figures, red/green/gray balance states (`mismatch` red, `ok` green, `skip` gray).
- Destructive or state-changing actions (confirm balances, audit, reverse-audit, restore backup) REQUIRE a confirm dialog.
- Keep existing Svelte + `@wailsio/runtime` patterns (`Events`, `WML`, generated `*Service.*` calls). Check `frontend/src/App.svelte` before adding new patterns.

## Completion Criteria

Before a task is complete:

```sh
gofmt -l ./...
go vet ./...
go build ./...
```

Frontend change also requires:

```sh
npm run check --prefix frontend
```

All must succeed. If any fails, the task is NOT complete.

---

## Definition of Done

A task is done only when ALL hold:

- Business-doc behavior implemented (import/recon/summary/voucher/balance per spec)
- Money uses `decimal`, balance-check and voucher-balance rules enforced
- Files in correct directories, Services registered in `internal/app/app.go`
- `gofmt`, `go vet`, `go build` pass; `frontend check` passes if UI touched
- No new warnings reasonably avoidable; no hand-edited bindings
- Anonymization verified: no real names/IDs outside `docs/raw/anonymization_mapping.tsv`
- Manual smoke path verified against sample rows (e.g. 07-10 `11970.00`, 07-11 `9256.80`)

If any item fails, the task is **not complete**.
